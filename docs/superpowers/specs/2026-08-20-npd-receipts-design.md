# Автоматические чеки НПД («Мой налог») — Design Spec

**Date:** 2026-08-20
**Status:** Approved (brainstorming) → ready for implementation plan

## Problem

Бот принимает платежи от физлиц через ЮKassa, но **не выдаёт покупателям чеки**.
Владелец бота — **самозанятый (НПД)**, и по 422-ФЗ обязан передать чек покупателю
по каждому расчёту. Сейчас этого не происходит ни автоматически, ни вручную.

Очевидный путь — объект `receipt` в запросе создания платежа ЮKassa — **закрыт**:
ЮKassa прекратила поддержку сервисов для самозанятых (чеки при платежах и возвратах,
выплаты самозанятым) **с 29 декабря 2025 года**. Онлайн-кассы по 54-ФЗ у самозанятого
нет и быть не может. На собственной странице для самозанятых ЮKassa прямо указывает,
что чек продавец выдаёт сам, «например, в сервисе Мой налог».

Значит, фискализацию надо делать в обход платёжного провайдера — напрямую в ФНС.

## Goals

- После каждого подтверждённого платежа доход автоматически регистрируется в «Мой налог».
- Пользователь получает ссылку на чек прямо в боте, сразу после оплаты.
- Email у пользователя **не спрашиваем** — чек НПД доставляется ссылкой, почта не нужна.
- Работает для всех платящих сценариев: пакеты генераций и разблокировка водяного знака за 50 ₽.
- Сбой фискализации **никогда** не блокирует выдачу оплаченного товара.
- Незакрытые чеки видны админу и добиваются вручную одной командой.
- Один платёж → максимум один чек, при любых гонках и рестартах.

## Non-goals

- Отмена/аннулирование чека при возвратах — отдельная итерация. В боте сейчас нет флоу
  возвратов вообще; редкие возвраты аннулируются в приложении «Мой налог» руками.
- Отправка чека на email / SMTP.
- Хранение и отображение истории чеков пользователю (кроме ссылки в момент оплаты).
- Поддержка юрлиц-плательщиков (`incomeType` кроме `FROM_INDIVIDUAL`) — у НПД платить
  через этот канал могут только физлица.

## Approach

**Свой тонкий async-клиент к `lknpd.nalog.ru` + отдельная таблица-очередь + fire-and-forget
регистрация после подтверждения платежа.**

Нужны ровно три вызова API (логин, refresh, создание дохода). `aiohttp` уже в зависимостях.
Готовые обёртки (`nalogo`, `moy_nalog`, `my-nalog`, `nalogovich`) слабо документированы,
разной степени живости, и это была бы заброшенная сторонняя зависимость в платёжном контуре.
Свой клиент — ~180 строк, полностью под контролем.

### Rejected alternatives

- **`receipt` в платеже ЮKassa** — технически невозможно: канал для самозанятых отключён
  29.12.2025, кассы по 54-ФЗ нет.
- **Полуавтомат** (бот шлёт админу данные, админ пробивает чек руками) — легально и просто,
  но ручной труд на каждый платёж, не масштабируется.
- **Регистрация ИП + онлайн-касса** — правильный путь при росте (и лимит НПД 2,4 млн ₽/год
  всё равно упрётся), но это не задача этой итерации.
- **Блокировать начисление кредитов до успешного чека** — максимальный комплаенс, но юзер,
  заплативший деньги, не получает товар из-за чужого API. Отклонено осознанно.

## Components

### 1. Клиент — `bot/services/npd_client.py` (новый)

Синглтон `npd_client = NpdClient()`, по образцу `kie_client` / `openai_client`.

Базовый URL: `https://lknpd.nalog.ru/api/v1`

| Метод | Endpoint | Назначение |
|-------|----------|------------|
| `_authenticate()` | `POST /auth/lkfl` | Логин по ИНН + паролю |
| `_refresh()` | `POST /auth/token` | Обновление по `refreshToken` |
| `add_income(name, amount_rub)` | `POST /income` | Регистрация дохода |

**Логин** — тело запроса:

```json
{
  "username": "<ИНН>",
  "password": "<пароль от ЛК>",
  "deviceInfo": {
    "sourceDeviceId": "<стабильный device id>",
    "sourceType": "WEB",
    "appVersion": "1.0.0",
    "metaDetails": {"userAgent": "<UA>"}
  }
}
```

Ответ содержит `token`, `refreshToken`, `profile.inn`. **Access-токен живёт ~1 час.**

**Регистрация дохода** — тело запроса:

```json
{
  "paymentType": "CASH",
  "ignoreMaxTotalIncomeRestriction": false,
  "client": {
    "incomeType": "FROM_INDIVIDUAL",
    "contactPhone": null,
    "displayName": null,
    "inn": null
  },
  "requestTime": "<ISO 8601>",
  "operationTime": "<ISO 8601>",
  "services": [{"name": "<наименование>", "amount": 149.0, "quantity": 1}],
  "totalAmount": "149.00"
}
```

Ответ: `{"approvedReceiptUuid": "..."}`.

**Ссылка на чек** строится локально:
`https://lknpd.nalog.ru/api/v1/receipt/{ИНН}/{uuid}/print`

`add_income` возвращает `(receipt_uuid, print_url)`.

**Управление токеном.** Токен и его expiry хранятся в памяти процесса. На `401` —
один прозрачный `_refresh()`; если и он не прошёл — полный `_authenticate()`. Дальше
ошибка отдаётся наверх как `NpdClientError`.

**`sourceDeviceId` обязан быть стабильным** — токен к нему привязан. Берётся из
`NPD_DEVICE_ID`; если переменная пуста, клиент генерирует UUID и пишет его в лог на
уровне WARNING с указанием вписать значение в `.env`. Плавающий device id означал бы
новый «вход» при каждом рестарте.

**Сумма чека — полная сумма платежа** (149 ₽, а не «минус комиссия ЮKassa»): доход
самозанятого — это то, что заплатило физлицо.

Пароль маскируется в логах по образцу `_mask_proxy()` из
[bot/services/openai_client.py](../../../bot/services/openai_client.py).

### 2. Хранение — таблица `npd_receipts`

Создаётся идемпотентно в `init_db()` в
[bot/services/user_limits.py](../../../bot/services/user_limits.py), рядом с остальными
миграциями:

```sql
CREATE TABLE IF NOT EXISTS npd_receipts (
    id            INTEGER PRIMARY KEY AUTOINCREMENT,
    payment_id    INTEGER NOT NULL UNIQUE,
    user_id       INTEGER NOT NULL,
    amount        INTEGER NOT NULL,          -- копейки, как в payments
    service_name  TEXT    NOT NULL,
    status        TEXT    NOT NULL DEFAULT 'pending',  -- pending | sent | failed
    receipt_uuid  TEXT,
    print_url     TEXT,
    attempts      INTEGER NOT NULL DEFAULT 0,
    last_error    TEXT,
    created_at    TEXT    NOT NULL DEFAULT (datetime('now')),
    updated_at    TEXT    NOT NULL DEFAULT (datetime('now'))
);
```

`payment_id UNIQUE` — **ключевая защита от двойного пробития**: ручная кнопка
«Проверить оплату» и фоновый polling могут гоняться друг с другом. Вставка идёт через
`INSERT OR IGNORE`; если строка уже есть — вторая попытка регистрации не стартует.

CRUD-запросы живут в новом `bot/services/npd_receipts.py`, а не в `user_limits.py`:
последний уже 859 строк, что выше лимита 800 из правил проекта. Для доступа к соединению
`_get_conn` получает публичный алиас `get_conn` (старое имя сохраняется).

### 3. Оркестрация — `bot/services/npd_receipts.py` (новый)

Публичная точка входа:

```python
async def issue_receipt(bot, payment_id: int, user_id: int, pkg) -> None
```

Логика:

1. `INSERT OR IGNORE` строки со статусом `pending`. Если вставки не было — выходим (чек уже в работе или пробит).
2. Попытка `npd_client.add_income(...)`.
3. Успех → `status='sent'`, сохраняем `receipt_uuid` + `print_url`, шлём пользователю
   отдельное сообщение с кнопкой **«🧾 Открыть чек»** (url = `print_url`).
4. Ошибка → `attempts += 1`, `last_error`, ретрай. Всего **до 6 попыток**: одна немедленная
   плюс 5 ретраев с задержками **2с, 5с, 15с, 60с, 300с**. Поле `attempts` считает все
   попытки, включая первую, поэтому условие остановки — `attempts >= 6`.
5. Ретраи исчерпаны → `status='failed'` + алерт админу с `payment_id`, суммой, датой и
   наименованием — достаточно, чтобы пробить чек руками в приложении.

Отдельное сообщение с чеком, а не дописывание в существующее: сообщение об успешной
оплате отправляется из четырёх разных мест с разными клавиатурами, и правка каждого
ради чека ломала бы их независимость.

**Sweep при старте.** `retry_pending_receipts(bot)` вызывается из
[bot/main.py](../../../bot/main.py) на старте: перебирает все `pending` и `failed` и
пробует заново. Закрывает дыру «сервер перезапустился посреди ретраев».

### 4. Точка встраивания — `bot/handlers/payment.py`

`confirm_payment()` возвращает `True` ровно в двух местах:
[payment.py:233](../../../bot/handlers/payment.py#L233) (ручная кнопка) и
[payment.py:325](../../../bot/handlers/payment.py#L325) (фоновый polling). Единой точки
доставки нет — в ручной ветке `_deliver_after_payment` вызывается только для
watermark-пакета.

В обе точки добавляется один вызов:

```python
# payment.py:325 — фоновый polling, bot есть в аргументах
asyncio.create_task(issue_receipt(bot, internal_id, user_id, pkg))

# payment.py:233 — у check_payment_status нет параметра bot, берём из callback
asyncio.create_task(issue_receipt(callback.bot, internal_id, user_id, pkg))
```

В обеих ветках `internal_id`, `user_id` и `pkg` уже определены выше по коду.

**Fire-and-forget** — фискализация не блокирует ни начисление кредитов, ни выдачу фото.
Это прямое следствие выбранной политики отказа.

### 5. Админ-команды — `bot/handlers/receipts.py` (новый)

Маленький роутер, только для `ADMIN_ID`:

- `/receipts_failed` — список незакрытых чеков (`pending` + `failed`) с суммами и датами
- `/receipts_retry` — принудительная добивка всех незакрытых

Отдельный файл, а не довесок к `payment.py` (427 строк): фискализация — своя зона
ответственности.

### 6. Конфиг — `bot/config.py`

Новые поля `Settings`:

| Поле | Тип | Назначение |
|------|-----|------------|
| `npd_inn` | `Optional[str]` | ИНН самозанятого |
| `npd_password` | `Optional[str]` | Пароль от ЛК `lknpd.nalog.ru` |
| `npd_device_id` | `Optional[str]` | Стабильный `sourceDeviceId` |
| `npd_enabled` | `bool = False` | Фича-флаг |

Аннотации — `Optional[str]`, **не** `str | None`: pydantic вычисляет их в рантайме, а
локальная разработка идёт на Python 3.9.6 (прод — 3.10). Это уже зафиксировано в CLAUDE.md.

Наименования услуг — константы там же:

- пакеты: `«Обработка фотографии (генерация портрета), {credits} шт.»`
- разблокировка: `«Обработка фотографии (снятие водяного знака)»`

При `npd_enabled=False` `issue_receipt` выходит сразу, ничего не записывая. Код едет на
прод мёртвым и включается после проверки.

## Data Flow

```
Пользователь оплатил
        │
        ▼
confirm_payment() → True ──► кредиты начислены, товар выдан  (синхронно, не ждёт чек)
        │
        └──► asyncio.create_task(issue_receipt(...))
                    │
                    ▼
             INSERT OR IGNORE npd_receipts (pending)
                    │  (если строка уже есть — выход)
                    ▼
             npd_client.add_income()
                    │
        ┌───────────┴───────────┐
        ▼                       ▼
     успех                   ошибка
        │                       │
   status='sent'          attempts++, backoff
   print_url              2с→5с→15с→60с→300с
        │                       │
        ▼                  исчерпано → status='failed'
  сообщение юзеру               │
  «🧾 Открыть чек»              ▼
                          алерт админу
```

## Error Handling

| Сценарий | Поведение |
|----------|-----------|
| Токен протух (401) | Прозрачный refresh, при провале — полный релогин |
| ФНС недоступна / 5xx | Ретрай с backoff, до 6 попыток суммарно |
| Ретраи исчерпаны | `status='failed'`, алерт админу, `/receipts_retry` для добивки |
| Бот перезапущен посреди ретраев | Sweep на старте перебирает `pending` + `failed` |
| Гонка polling vs ручная кнопка | `payment_id UNIQUE` + `INSERT OR IGNORE` |
| `npd_enabled=False` | Мгновенный выход, ничего не пишется |
| Неверные креды | `NpdClientError` в лог, `failed`, алерт админу |

Ни один из сценариев не мешает пользователю получить оплаченное.

## Testing

TDD — тесты пишутся до реализации. В чистые функции выносятся и покрываются без сети:

- сборка тела запроса `add_income` (суммы, `totalAmount`, ISO-время, структура `services`)
- построение `print_url` из ИНН и uuid
- логика протухания токена (нужен ли refresh на момент T)
- расчёт задержки backoff по номеру попытки

Стиль — как у [tests/test_prompt_fallback.py](../../../tests/test_prompt_fallback.py):
self-contained, запускается `python3 tests/test_npd_client.py`, без pytest и без `.env`.

Интеграционная проверка — один реальный платёж на 50 ₽ после включения флага на проде,
с последующей сверкой чека в приложении «Мой налог».

## Rollout

Двухшаговая раскатка, как принято в проекте:

1. Деплой кода с `NPD_ENABLED=false` — прод работает как раньше, ничего не меняется.
2. Заполнить `NPD_INN` / `NPD_PASSWORD` / `NPD_DEVICE_ID`, включить флаг, провести один
   реальный платёж 50 ₽, проверить чек в «Мой налог» и ссылку в боте.

Файлы деплоятся по одному через `/tmp` + `sudo cp` с проверкой содержимого перед стартом
сервиса (см. CLAUDE.md / память проекта — рекурсивный `scp -r` может молча не перезаписать).

## Risks

- **API `lknpd.nalog.ru` неофициальный.** ФНС может сменить контракт без предупреждения.
  Смягчено ретраями, алертами и ручной добивкой, но не устранено.
- **Пароль от налогового кабинета лежит на сервере** в `.env` (chmod 600, вне git).
- **Лимит НПД 2,4 млн ₽/год**, платить могут только физлица. При приближении к лимиту
  потребуется переход на ИП — и тогда исходный вариант с `receipt` в ЮKassa станет доступен.
- **Токен привязан к device id.** Нестабильный `NPD_DEVICE_ID` = постоянные релогины.
